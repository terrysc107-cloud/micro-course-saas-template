## Edit vs. Refactor

- **Edit**: a targeted change to fix a bug, add a prop, or update a value
- **Refactor**: restructuring code to improve it without changing its behavior

Both use the same Claude Code workflow, but refactoring requires more care.

## Surgical Edits

For small, precise changes, be surgical:

```
> In @src/components/PricingCard.tsx, change the "Buy Now" button 
  label to "Get Instant Access" and change its color from bg-blue-600 
  to bg-brand-600. Do not touch anything else.
```

The "do not touch anything else" constraint is your safety rail. Without it, Claude might helpfully refactor the whole component while it is in there.

## Renaming Across the Codebase

```
> Rename the function `getUserData` to `fetchUserProfile` everywhere 
  in the codebase. Update all imports and usages.
  Files to check: @src/lib/, @src/hooks/, @src/api/, @src/components/
```

Claude handles the find-and-replace with context, ensuring it only renames call sites and not string literals that happen to contain the same text.

## Type Safety Upgrades

Common in JavaScript projects moving to TypeScript:

```
> @src/utils/formatting.js uses no types. 
  Convert it to TypeScript:
  - Add explicit parameter and return types to every function
  - Replace any `any` with proper types
  - Rename to formatting.ts
  - Do not change the logic, only add types
```

<Callout type="warning">Never ask Claude to refactor an entire large file in one prompt — it will miss edge cases, lose track of subtle dependencies, and produce a diff too large to review meaningfully. Break refactors into logical steps: extract one concept at a time, run tests between each step, and accept or reject independently.</Callout>

## Safe Refactoring Pattern

For important code, always write tests first:

```
Step 1:
> @src/lib/scoring.ts has no tests. Before we refactor it, 
  write comprehensive unit tests for the calculateScore() function 
  covering: normal input, empty input, boundary values (0 and 100), 
  and invalid input. Put tests in @src/__tests__/scoring.test.ts

Step 2:
> Run the tests to confirm they pass

Step 3:
> Now refactor calculateScore() to be more readable — 
  extract the category weighting into a named constant object,
  replace the nested ternary with a switch statement.
  The tests we just wrote must still pass.
```

This pattern — test then refactor — is bulletproof.

<Callout type="tip">When asking Claude to refactor, always tell it the style or pattern to follow: "refactor this to match the pattern in @src/lib/auth.ts" or "use the same error-handling approach as the other routes in this folder." Without a reference, Claude picks a style — with one, it matches yours.</Callout>

## Removing Dead Code

```
> @src/lib/legacy-api.ts appears to be unused. 
  Before deleting it, check @src for any file that imports from it.
  If it is truly unused, confirm and I will accept the deletion.
```

Claude scans your project before suggesting a deletion. You stay in control.

## Splitting Large Files

When a file grows too large:

```
> @src/lib/utils.ts has grown to 400 lines and mixes 
  string utilities, date utilities, and number utilities.
  Split it into three files:
  - @src/lib/utils/strings.ts
  - @src/lib/utils/dates.ts  
  - @src/lib/utils/numbers.ts
  
  Keep a @src/lib/utils/index.ts that re-exports everything 
  so existing imports still work.
```

The re-export barrel file (`index.ts`) is key — it means zero import updates needed elsewhere.

## Performance Refactors

```
> @src/components/DataTable.tsx re-renders on every keystroke 
  because the filterData function is recreated on each render.
  Memoize the filtered data with useMemo — only recalculate 
  when the data prop or filter string changes.
```

Claude understands React's performance patterns and applies them correctly.

## Summary

Edit surgically, test before refactoring anything important, and always include the "keep the same external behavior" constraint. Claude Code makes refactoring faster and safer than doing it manually.

<KeyPoint>For safe refactoring: write tests for the existing behavior first, then refactor with the constraint that those tests must still pass — this gives you an objective definition of "correct" that survives the change.</KeyPoint>
