## Teams That Use Claude Code Well

AI-assisted development on a team is a multiplier — if the team has standards. Without them, you get inconsistent code that is hard to review and maintain.

## The Team CLAUDE.md

The single most important standardization: one `CLAUDE.md` in the repo that everyone contributes to and uses.

It should include:
- Tech stack and key dependencies
- Naming conventions agreed on by the team
- Architecture decisions and why they were made
- Code patterns to follow
- What NOT to do (and why)
- Current work in progress (updated on each PR)

When Claude writes code to your CLAUDE.md spec, it matches what a teammate would write. That is reviewable.

<Callout type="tip">Keep a shared CLAUDE.md in the repo and treat it like code — review changes to it in PRs, require team consensus on changes to conventions, and update it in the same PR where you establish a new pattern. A well-maintained team CLAUDE.md is worth more than any amount of onboarding documentation.</Callout>

## Code Review Norms

AI-generated code gets the same review as human code. Period.

Some teams add a lightweight PR template section:

```markdown
## AI Assistance
- [ ] No AI assistance used
- [ ] Used Claude Code for: [describe what]
- [ ] All AI-generated code was reviewed and tested
```

Transparency helps the team learn from each other's prompts and builds trust.

<Callout type="info">Establish team conventions for prompt patterns early — for example, "always reference @CLAUDE.md at the start of a session," "always include the framework version in stack-specific prompts," or "always use the pre-ship checklist prompt before merging." Shared patterns produce more consistent output and make AI-generated code easier to review.</Callout>

## Sharing Prompts

When you find a prompt that works really well, share it:

- Add it to the team CLAUDE.md under `## Useful Prompts`
- Share it in your team chat
- Add it to your project's `prompts/` directory

A library of tested prompts is a team productivity asset.

## Onboarding New Developers

When someone joins the team:

```
> I am a new developer joining this team.
  Read @CLAUDE.md and then walk me through:
  1. How the app is structured
  2. The patterns used for authentication
  3. How to add a new API route correctly
  4. The testing conventions
  
  Then quiz me on the key conventions to make sure I got them.
```

This is a better onboarding experience than reading documentation alone.

## Preventing Style Drift

One risk of team Claude Code usage: three developers using Claude with slightly different prompts produce three different styles of code. Fix this with:

1. Regular CLAUDE.md updates after each major PR
2. Code review comments that say "update CLAUDE.md with this pattern" when good patterns emerge
3. Monthly team review: is our CLAUDE.md still accurate?

## When Not to Use Claude Code in a Team

- **Architecture decisions** — these require human discussion, not AI generation
- **Security architecture** — the whole team should understand how security works
- **Business logic decisions** — Claude does not know your users or business goals
- **Anything that should be human-owned** — if it goes wrong, a human needs to understand it

Use Claude for implementation. Keep strategy and architecture human.

## Summary

A shared, maintained CLAUDE.md is the foundation of team AI usage. Review AI code like human code. Share good prompts. Be transparent. Keep architecture human.

<KeyPoint>A team that shares one maintained CLAUDE.md, reviews AI code like human code, and builds a library of tested prompt templates will compound efficiency gains month over month — the shared context makes every developer on the team better, not just the ones who are power users of Claude Code.</KeyPoint>
