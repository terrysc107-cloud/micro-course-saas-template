## Slow Down Here

Everything else in this build is reversible. Bad button? Delete it. Bad color? Nobody died. `git reset` your way out of lesson 4 and lose an hour.

**Saved data is different.** Once the page has stored tasks, changing the shape is not an edit — it is a translation of items you already care about. The beginner version of a "migration" is: you renamed a field and yesterday's list vanished.

So this is the lesson where you go slower on purpose. Not because JSON is hard. Because this is where being wrong is expensive.

<Callout type="warning">Agents are good at inventing a tidy shape and have no concept of what your saved items are worth. A rewrite that "simplifies" the object is also, if you already have data, a data-loss event.</Callout>

## Model the Data First

Still in plan mode, with the brief in context:

```
> Plan mode. Settle the data shape before any save logic.

  For a Task, give me: field name, type, can it be empty, default,
  and the reason it exists — mapped to a done-criterion.

  Then answer:
  1. What does done=false mean, as distinct from a missing field?
  2. How is "done" constrained — true/false only, not "Yes"?
  3. What happens if localStorage is empty or corrupted?
  4. Which fields the Open view filters on?
```

Question 2 is the one that repays reading. If `done` is a string, you will get `"Yes"`, `"true"`, and `""` — and the Open view will guess wrong. Use a real true/false value.

## Write the Save Rules Down

Now, and only now:

```
> Write the save and load functions we planned.
  Requirements:
  - done is true or false, never a string.
  - Empty title is rejected before save.
  - Load treats missing or broken storage as an empty list, not a crash.
  - Show me a two-line example of a saved task.
```

### Review by hand

Read the functions. Not the summary. The functions.

- Does load survive an empty store?
- Does save refuse an empty title?
- If you already had items, would a field rename break them?

<Callout type="warning">"It ran without errors" is not "it did the right thing." A save can succeed and store garbage. Open the browser's developer tools, look at localStorage, and read the actual value.</Callout>

## Prove It Works

Add one task by hand (or with a tiny snippet Claude gives you). Refresh. Is it there? Add an empty title. Was it rejected? Mark one done. Does Open hide it?

Those are the same checks you will automate in lesson 5. Meet them in person first.

## Commit Separately

```bash
git add app.js
git commit -m "data: task shape with boolean done and empty-title reject"
```

Its own commit. If the look of the page in lesson 4 needs reverting, you want to revert the page without touching the save rules.

## Before You Move On

- Every field maps to a done-criterion
- `done` is true/false, and you watched a bad value get refused or corrected
- Empty title is rejected
- Data work is committed on its own

<KeyPoint>Saved data is the one part of this build where being wrong is expensive. Constrain values in the save path — a rule that only exists in your head is a rule that only holds while you are watching — and look at the stored value yourself.</KeyPoint>
