## The Check That Would Have Caught It

Most AI-written tests are green and worthless. They assert that add adds and list lists — which would keep passing through a rewrite that broke your product.

The standard:

> **Would this check have failed before the fix?**

If no, it's decoration. Start from real failures — lesson 3's empty title, and whatever you actually got wrong in lesson 4.

You do not need a fancy test runner. A small file you run with `node` is enough, or a list of functions Claude can execute:

```
> Write checks for the Open rule and the empty-title reject in @app.js.

  - empty title -> not saved
  - a task with done=false -> isOpen is true
  - a task with done=true -> isOpen is false

  Then: break the empty-title reject on purpose and show me which
  checks fail. If none fail, the checks are wrong, not the code.
```

That last instruction is the whole lesson. **A suite that stays green when you break the code is not a suite.**

<Callout type="tip">Break the code, watch the checks. If they go red, you have tests. If they stay green, you have a green checkmark. The difference is invisible until you look.</Callout>

## Test the Done-Criteria

Walk the brief. For each criterion: what fails if this breaks?

Criterion 6 — empty title rejected with a message, not saved — is two claims:

```
> Two separate checks:
  1. The user sees a message.
  2. Nothing was written to storage.
```

<Callout type="warning">When a check fails, the failure is information. The default agent instinct is to make it green, and the fastest way is to weaken the assertion. Watch for that in the diff.</Callout>

## The Review Pass

Your build session wrote every line. It also holds every reason each line seemed correct. That makes it the wrong reviewer.

`/clear`, or start a new session:

```
> You're reviewing a feature you didn't write. Adversarial read, not a summary.

  Spec: @brief.md
  Diff: run `git diff` against the first commit, or `git log -p`.

  Find:
  1. Behavior that contradicts the brief's done-criteria.
  2. Anything built that the brief lists as a non-goal.
  3. Rules implemented in more than one place.
  4. Error paths with no handling.
  5. Checks that would still pass if the behavior they name broke.

  Cite file and line. Do not fix anything. Do not tell me what's good.
```

"Do not tell me what's good" is not stylistic. Given room, a review comes back 70% praise, and the praise is where your attention goes.

<Callout type="info">A fresh session is zero setup. Neither it nor a later review subagent is a substitute for you reading the diff — they're a second reader who isn't invested in the answer.</Callout>

## Triage the Findings

**Fix now.** Contradicts a done-criterion. Rule duplicated. Empty title still saves.

**Write down, don't fix.** Real, but out of scope — "no due dates" is a true observation about a brief that says no due dates.

**Disagree.** Some findings are a generic best practice applied where it doesn't hold. You have the context. Say no.

```
> Findings 1 and 4: fix. One commit each.
  Finding 2: out of scope, the brief lists it as a non-goal. Skip.
  Do not fix anything I didn't list.
```

## Before You Move On

- Every check came from a real failure or a real done-criterion
- You broke the implementation on purpose and watched checks go red
- The review ran in a context that didn't write the code
- Findings are triaged: fixed, deferred, or explicitly declined

<KeyPoint>A check that would still pass if the behavior broke is decoration — break the code on purpose and watch it go red. And review in a context that didn't write the code.</KeyPoint>
