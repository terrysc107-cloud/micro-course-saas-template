## Why Plan Mode Exists

Plan mode reads files and does not edit source files. Cycle to it with `Shift+Tab`.

What it actually buys you is a **checkpoint that costs nothing to fail**. Rejecting a plan costs a paragraph. Rejecting an implementation costs a revert and a conversation now full of an approach you don't want.

<Callout type="info">Plan mode is a permission mode, enforced by Claude Code rather than by the model. This is why it's stronger than a politely-worded prompt. <a href="https://code.claude.com/docs/en/permission-modes">Permission modes docs</a> — behavior changes, check them.</Callout>

## Ask for the Plan

Hand over the brief. Stay in plan mode.

```
> Read @brief.md — that's the full scope for this build.

  Still in plan mode. Do not write code. Propose a plan that covers:

  1. The data shape: every field on a task, and what "done" means.
  2. Persistence: localStorage or a file, and why.
  3. The file-by-file list: exact names, and one line on what each does.
  4. Build order: what I can check after each step.
  5. Everything in the brief's non-goals that you were tempted to build.
  6. Every decision you are uncertain about.
```

Sections 5 and 6 are the ones people cut. Don't. An agent asked to build a checklist will want tags, due dates, and reminders because those things are *in* checklists in general. Naming the temptation kills it before it costs you a diff.

## Grading the Plan

Read it hostilely. Look for adjectives standing in for decisions.

| Plan says | The unmade decision |
|---|---|
| "the usual files" | Which files? At which names? |
| "handle saving" | localStorage? A JSON file? When does it write? |
| "add tests" | For which of the six done-criteria? |
| "wire it up" | Nobody knows, including the author |

Compare against a plan that has actually decided:

> Create `index.html` (the page), `styles.css` (layout), and `app.js` (behavior).
> A task is `{ id, title, done }`. `done` is true or false, never a string.
> Save the array in localStorage under the key `daily-checklist`.
> `isOpen(task)` lives in `app.js` and returns `task.done === false`.
> Empty title is rejected in the add function before anything is saved.

Every noun is named. That plan is reviewable.

<Callout type="warning">Vagueness in a plan is not a communication problem you can fix by reading generously. It is a signal that the decision has not been made. Accepting it moves the decision into a diff.</Callout>

## Rejecting a Plan

Reject with specifics:

```
> Rejecting this. Three problems:
  1. "Usual files" is not a decision. Name them.
  2. I cannot tell where empty titles are rejected.
  3. Your file list has eight files. The brief has six criteria
     and excludes accounts and hosting. Justify each file or drop it.
  Revise. Still no code.
```

Two or three rounds is normal. If you're on round five, fix the brief — Claude is reproducing its ambiguity.

## Scaffold

Plan approved. Cycle out of plan mode. Scaffold means **structure, not behavior**:

```
> Approved. Scaffold only:
  - Create the files from the plan, in the names from the plan.
  - Functions may exist as names that throw "not implemented".
  - No real save logic, no styling beyond a readable page.
  Then stop.
```

Read every file. Does the list match the plan? Extra files are scope creep that survived the plan review.

## Commit the Scaffold

```bash
git add -A
git commit -m "scaffold: daily checklist files"
```

Commit it even though nothing works. This is a known-good floor. If the next lesson goes sideways, you return here and you've lost a lesson, not a day.

## Before You Move On

- The plan named every file and the task shape
- You rejected at least one version of it
- Scaffolded files match the approved plan
- The scaffold is committed on a branch that isn't `main` (or, if this is your only folder, you at least have a commit you can return to)

<KeyPoint>Plan mode is the one checkpoint where being difficult is free — rejection costs a paragraph, not a revert. Read the plan for adjectives standing in for decisions, because those are deferrals you will pay for later in a diff.</KeyPoint>
