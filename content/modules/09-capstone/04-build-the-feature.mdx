## One Increment at a Time

You have a shape and a scaffold. The temptation is one prompt: "build the checklist." Don't. You will not review 600 lines. You will skim them.

The rule: **each increment ends at a state you can verify and commit.**

For this build, roughly:

1. Save and load — add a task in the console or a tiny helper, refresh, it is still there
2. The list on the page — renders real tasks
3. The add form — with empty-title rejection
4. Mark done / not done
5. The Open view — using the rule from lesson 3

Five increments. Five reviews. Five commits.

<Callout type="tip">A good increment boundary answers "what can I check when this is done?" with one sentence. "I can create a task and read it back after refresh" is an increment. "Set up the app" is not.</Callout>

## Increment 1: Save and Load

```
> Increment 1 only: save and load. Nothing else.
  Implement the functions we planned in @app.js.
  When you're done, show me how to prove a task round-trips:
  save one, reload, read it back.
  Stop after this. Do not start increment 2.
```

"Stop after this" earns its place. Left alone, an agent that finishes a coherent piece reaches for the next one.

### Review the diff

**1. Does it match the plan?** If the plan said `isOpen` is a function and this diff inlines the check, that's drift. Reject it.

**2. What did it touch that I didn't ask for?** `git diff --stat` first. An unexpected file is the highest-signal thing in this lesson.

**3. What happens when it's wrong?** Empty title? Broken storage? Those paths are where agent-written code is thinnest.

<Callout type="warning">`git diff --stat` before you read a single line. The file list is a claim about scope, and it's the fastest lie to catch.</Callout>

Then run the proof yourself. Not "Claude says it works."

```bash
git add app.js
git commit -m "feat: save and load tasks"
```

## Increments 2 Through 5

Same shape every time. Scope it, build it, `--stat` it, read it, run it, commit it.

**Increment 2, the list.** Zero tasks and one task are done-criteria. Check them now, in the browser.

**Increment 3, the form.** "Rejected with a message" and "not saved" are two claims. Check both. Refresh after a rejected submit — is a blank task there anyway?

**Increment 4, done toggle.** This is where `done` becomes a string if you are not watching.

**Increment 5, Open view.** The rule already exists. Watch for Claude rewriting it inline rather than calling the function.

## When It Goes Off the Rails

It will. You ask for a small fix, the diff touches six files. Claude apologizes, tries again, produces something worse.

**Do not argue with a bad context.**

```bash
git reset --hard HEAD    # back to your last good commit
```

Then `/clear`. Then re-scope, smaller:

```
> Fresh start. Read @app.js.
  One thing only: the Open view is showing done tasks.
  Find the cause. Do not fix it yet — tell me where it is and why.
```

This is why increments and commits matter. `git reset --hard` is only cheap if your last good commit is twenty minutes back.

<Callout type="warning">The moment you notice you're explaining the same thing a third time, stop. Reset, re-scope, and you'll usually have it fixed in one turn.</Callout>

## Before You Move On

- All five increments built, reviewed, and committed separately
- You ran `git diff --stat` on every one before reading it
- Every done-criterion from the brief has behavior behind it
- The Open rule and the empty-title reject each exist in exactly one place

<KeyPoint>Small increments aren't neatness — they're what makes reverting cheap, and cheap reverting is what lets you kill a bad context instead of negotiating with it.</KeyPoint>
