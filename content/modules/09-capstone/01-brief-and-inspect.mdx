## The Build

You are building a **local Daily Checklist**. A page you open in your browser. You add a task, see it in a list, mark it done, and still see it after you refresh the page.

That is deliberately small. A beginner can finish it. It is still real enough that you will hit data shape, empty states, and bad input — the same problems a bigger app has, without Next.js, a database, or a deploy.

**The workflow is the product.** The checklist is the excuse to run it once end to end:

**Inspect → Plan → Build → Review → Test → Ship**

<Callout type="info">
After you are ready — meaning you have finished this local build once — you may run the same six lessons on the older **Lead Follow-Up Command Center** (Next.js, a real data store, a preview deploy). That path is optional. Do not start it as your first capstone.
</Callout>

## Write the Brief First

Before you open Claude Code. Before you create files.

Plan mode, review, and QA all measure your work against *something*. If that something only exists in your head, it changes every time you are tired or impressed. A brief you wrote an hour ago is a witness you cannot quietly rewrite.

A build brief is one page. Start from [our build brief template](/downloads/build-brief-template.md). Fill in every section.

Six sections:

1. **Problem** — what is broken today, in one or two sentences
2. **User** — who, and what they are doing when they touch this
3. **Done-criteria** — the checkable list that defines finished
4. **Non-goals** — what you are explicitly not building
5. **Constraints** — stack, data rules, anything non-negotiable
6. **Rollback plan** — how you undo this if it goes wrong

### The brief for this capstone

```
PROBLEM
I keep daily tasks in my head or in scattered notes. I forget
what is still open, and I cannot see yesterday's leftovers.

USER
Me. I open this once in the morning, for about two minutes,
before I start work.

DONE-CRITERIA
1. I can add a task with a title and it is still there after I
   refresh the browser.
2. The list shows every task and whether it is done.
3. I can mark a task done and mark it not-done again.
4. An "Open" view shows only tasks that are not done.
5. Zero tasks and one task both render without looking broken.
6. An empty title is rejected with a message, not saved.

NON-GOALS
- No accounts. No login. Single person on this computer.
- No internet required after the files exist.
- No database server. No Next.js. No hosting company required.
- No sharing, no mobile app, no reminders.

CONSTRAINTS
- Three files is enough: index.html, styles.css, app.js.
- Data lives in the browser (localStorage) or a local JSON file.
- Must open by double-clicking index.html or using a simple local server.

ROLLBACK PLAN
Git is the undo. Every good increment is a commit. If a change
is bad, return to the last good commit. Nothing is deployed.
```

Read done-criterion 4 again. "Open" means not done — write that down. If you leave it vague, Claude will invent a meaning in the code and you will find out in the review.

<Callout type="tip">If a done-criterion can't be checked by someone who didn't build the feature, it isn't a criterion — it's a wish. "Tasks are easy to see" is a wish. "The Open view lists only tasks that are not done" is a criterion.</Callout>

## Now Inspect

You have a brief. You still don't get to build.

Start in **plan mode** — press `Shift+Tab` until you're in plan. Plan mode reads files and does not edit source. It makes "Claude accidentally started building" structurally impossible.

<Callout type="warning">Permission modes are enforced by Claude Code, not by the model. Typing "don't edit anything yet" into your prompt is a request. Plan mode is a rule. Use the rule. See the <a href="https://code.claude.com/docs/en/permission-modes">permission modes docs</a> — details change.</Callout>

### If you're starting from an empty folder

Create a folder named `daily-checklist`, run `git init` inside it, save your brief as `brief.md`, and inspect the ground:

```
> We're building a local daily checklist. Before any code:
  list the files in this folder, read brief.md, and tell me
  exactly what is already here. If something is not present,
  say "not present" rather than assuming a default.
```

That last sentence matters. It gives Claude permission to say "I don't know."

## Grading the Inspection

You are reading the response for one thing: **is it grounded in files, or is it grounded in vibes?**

Signals it's real: claims carry file paths that exist; it quotes actual text; it says "not present" about at least one thing.

Signals it's confabulating: fluent, confident, generic; names a file or library you don't have; zero uncertainty.

If you get the second kind, run `/clear` and re-ask with `@brief.md` named explicitly. Resetting a bad inspection costs two minutes. Building on one costs the afternoon.

## Before You Move On

Run [the preflight checklist](/downloads/preflight-checklist.md) once.

You are done with this lesson when:

- The brief exists as a file, with all six sections filled in
- Claude has described the folder in terms you recognize, with paths
- Not one source file has been edited (the brief itself is not source)

<KeyPoint>The brief is the fixed point that everything downstream gets measured against. Write it before you have a diff you're attached to, and make Claude prove it has read your folder before it proposes anything.</KeyPoint>
