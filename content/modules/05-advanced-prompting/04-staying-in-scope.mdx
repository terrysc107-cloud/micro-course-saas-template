## The Scope Problem

Claude is helpful by nature — sometimes too helpful. It spots code that could be better, adds things "while it is in there," and refactors things you did not ask it to refactor.

In small doses this is great. But when you are trying to make a surgical change, unexpected edits are bugs waiting to happen.

<Callout type="warning">Scope creep most often appears in refactoring prompts — you ask Claude to rename a function and it also extracts a helper, updates the tests, and adds a comment. These changes may all be improvements, but they make the diff harder to review and add risk to what was supposed to be a simple rename. Lock down scope explicitly.</Callout>

## The One Rule

Add this to every prompt where scope matters:

```
> Update the label on the Submit button to say "Complete Purchase".
  Only change this text. Do not modify anything else in the file.
```

"Do not modify anything else" is the most powerful scope constraint you have.

## Being Specific About What to Change

The more precisely you describe the target, the less room there is for drift:

**Vague (risky):**
```
> Fix the checkout form
```

**Specific (safe):**
```
> In @src/components/CheckoutForm.tsx, in the handleSubmit function 
  (around line 45), the setLoading(false) call is missing in the 
  catch block. Add it so the button resets when the request fails.
  Do not change anything else.
```

## Handling Unrequested Changes

When Claude does something useful but outside your scope:

```
You: > Add a loading spinner to the Submit button in @src/components/Form.tsx

Claude: [adds spinner, also fixes a typo in an error message, 
         and adds missing aria-label attributes for accessibility]

You: Accept the spinner change, reject the other two.

Later:
You: > Now fix that typo in the error message on line 78 — change 
      "Sumbit" to "Submit"
```

Accept what you asked for. Audit the rest. Come back for the good stuff deliberately.

## Scope Constraints for Refactoring

Refactoring is the highest-risk area for scope creep:

```
> Refactor the calculateScore function in @src/lib/scoring.ts
  to be more readable by extracting the weight constants to a 
  named object at the top of the file.
  
  Constraints:
  - Only change calculateScore and add the constant object
  - Do not change any other functions in the file
  - Do not change the function signature or return type
  - The existing tests must still pass
```

Four explicit constraints. Claude knows exactly where the walls are.

## Multi-File Changes

When Claude needs to touch multiple files:

```
> Rename the type 'Student' to 'StudentProfile' everywhere.
  
  Files to update:
  - @src/types/index.ts (the type definition)
  - @src/lib/students.ts (function signatures)
  - @src/api/onboarding/student/route.ts (usage in handler)
  
  Do not update any other files. Do not change any logic — 
  this is a pure rename.
```

Explicitly listing the files prevents Claude from going exploring.

<Callout type="tip">The most effective scope-limiting phrase is "only change X, do not touch Y" — be explicit about what is off-limits, not just what you want changed. For example: "only modify the handleSubmit function, do not change the form layout, the validation logic, or any other functions in this file."</Callout>

## Using /clear to Reset Scope

When you are done with one task and moving to the next, use `/clear` to reset the conversation. This prevents Claude from thinking the new task is related to the old one and "helpfully" making connections across tasks.

## Summary

Scope is about being the architect. You decide what changes, when, and where. The phrases "only change," "do not touch," and listing explicit file targets are your most powerful tools for staying in control.

<KeyPoint>Staying in scope is staying in control — use "only change X, do not touch Y" in every prompt where precision matters, and always explicitly list the files Claude is allowed to modify; this single habit prevents most of the "Claude did something I did not ask for" frustrations.</KeyPoint>
