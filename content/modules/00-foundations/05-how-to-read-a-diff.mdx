## This Is The Safety Skill

A **diff** is a picture of a change. It shows the old lines and the new lines.

Claude Code will often give you a summary: "I added a heading and fixed a typo." Summaries are useful. They are not the change. The change is the lines.

If you only read the summary, you will accept plausible work that is subtly wrong — a deleted sentence you still needed, a file you did not ask to touch, a password that should never have been added.

This course will ask you to read diffs for the rest of the way. That is the point.

## What The Symbols Mean

A common format looks like this:

```diff
--- a/hello.md
+++ b/hello.md
@@ -1,2 +1,3 @@
 This is my practice folder.
-I will learn Claude Code someday.
+I am learning Claude Code today.
+I will read every diff.
```

Read it like this:

- `--- a/hello.md` — the old file
- `+++ b/hello.md` — the new file
- `@@ ... @@` — which line numbers are shown (you can ignore the math at first)
- A line with no prefix — unchanged, shown for context
- A line starting with `-` — removed
- A line starting with `+` — added

So the story of this diff: one line was replaced, and a new line was added. Nothing else in the file moved.

<Callout type="tip">
Read the file name first, then the `+` and `-` lines. If the file name is a surprise — a file you did not ask to change — stop. That is the cheapest catch in the whole workflow.
</Callout>

## A Three-Question Review

Every time you see a diff, ask:

**1. Which files changed?**
Use `git status` or `git diff --stat`. Unexpected files are a stop sign.

**2. Do the added and removed lines match what I asked for?**
If you asked to add one sentence and the diff rewrites the whole file, that is too much. Say no.

**3. Is there anything I do not understand?**
A line you cannot explain is a line you should not accept yet. Ask:

```text
Explain the change on line 12 of hello.md in plain language.
What happens if I keep it? What happens if I reject it?
```

<Callout type="warning">
Slow down extra if a diff touches passwords, payment, accounts, or anything that deletes files. Those are the expensive mistakes. A confident summary is least useful exactly when the stakes are high.
</Callout>

## Practice On Your Own File

In `hello.md`, make a small edit yourself. Save. Then:

```bash
git diff
```

Read it out loud. Point at each `-` and `+` and say what it did.

Then undo the unsaved-to-git edit if you want a clean file:

```bash
git checkout -- hello.md
```

That last command throws away uncommitted changes to that file and restores the last commit. Only use it when you *mean* to throw the edit away.

Or keep the edit:

```bash
git add hello.md
git commit -m "Practice reading a diff"
```

## What "I Don't Know" Sounds Like

You are allowed to say:

- "I do not know what this line does. Explain it."
- "This file should not have changed. Revert it."
- "This is bigger than I asked. Do only the heading change."

Those are competent reviews. Approving a mystery to feel faster is not.
