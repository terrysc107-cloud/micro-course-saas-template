## The Most Important Habit in Claude Code

The single habit that separates effective Claude Code users from people who create messes is this: **review every change before accepting it**.

This sounds obvious. In practice, developers get into a flow and start hammering `y` without reading. That is when bugs, security holes, and unwanted changes slip in.

<Callout type="warning">Never develop the habit of pressing `y` without reading the diff — even on small changes. The moment you start skipping the review step, you lose the primary safety net that makes Claude Code safe to use in production codebases. Speed is not worth a security hole.</Callout>

## Reading the Diff

When Claude proposes a change, it shows a diff:

```diff
  // src/api/users.ts
  
  export async function getUser(id: string) {
-   const user = await db.query(`SELECT * FROM users WHERE id = ${id}`);
+   const user = await db.query('SELECT * FROM users WHERE id = $1', [id]);
    return user;
  }
```

Lines starting with `-` (red) are being removed. Lines starting with `+` (green) are being added.

In this example, Claude fixed a SQL injection vulnerability by parameterizing the query. If you had accepted without reading, you might have missed that this was a security issue in your original code — now fixed.

## What to Check in Every Diff

**Scope** — Did Claude only touch what you asked? Watch for unrelated changes snuck in.

**Logic** — Does the new code actually do what you asked? Read it like a code review.

**Edge cases** — Are there obvious missing error checks, null checks, or boundary conditions?

**Style** — Does it match your project's conventions (naming, formatting, imports)?

**Security** — Are there any credentials, hardcoded values, or unsafe patterns?

## Asking Questions Before Accepting

<Callout type="tip">Before asking Claude to make an edit, ask it to explain its plan first: "Before you make any changes, explain what you're going to do and why." This surfaces misunderstandings before they become code you have to undo — and saves you from reviewing a diff that was built on a wrong assumption.</Callout>

You do not have to accept or reject immediately. You can ask questions:

```
You: > Add a rate limiter to the login endpoint

Claude: [shows diff adding rate limiting middleware]

You: > Before I accept — why did you put this in middleware 
      instead of directly in the route handler?

Claude: [explains the tradeoff]

You: > Got it, that makes sense. Accept.
```

This dialogue makes you a better developer — you are learning from every change, not just shipping blindly.

## Rejecting and Redirecting

Press `n` to reject a change, then explain what you actually wanted:

```
You: > Add form validation to the sign-up form

Claude: [adds client-side only validation]

You: > n — I need server-side validation too. The client-side 
      validation is fine, but also add validation in the API 
      route at @src/app/api/signup/route.ts
```

You have not lost any work. Claude still holds all the context. Just redirect.

## Partial Acceptance

Sometimes Claude changes three files and two are great but one is wrong. You can accept the good ones and reject the bad one:

```
Accept change to src/lib/auth.ts? (y/n) y
Accept change to src/components/LoginForm.tsx? (y/n) y  
Accept change to src/app/layout.tsx? (y/n) n
```

Then give Claude specific feedback on the rejected file.

## The Golden Rule

**You are the architect. Claude is the builder.**

Claude can write code faster than you can, but it does not know your business logic, your team's conventions, your security requirements, or your users. You do. Stay in the loop on every change and you will never lose control of your codebase.

<KeyPoint>You are the architect and Claude is the builder — reviewing every diff before accepting is not optional overhead, it is the habit that lets you stay in control of your codebase while moving at AI speed.</KeyPoint>

This loop — prompt, read diff, ask questions, accept or redirect — is what makes Claude Code a multiplier rather than a liability.
