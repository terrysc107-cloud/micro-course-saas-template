Five tiers. Each one has a different read pattern, and that is the only reason
the system survives contact with time.

## Tier 1 — The index

One file that says what is here, what to read when, and what never to touch.

This sounds like documentation. It is not. It is the **retrieval strategy**. A
run reads the index, decides what it needs, and fetches only that. Without it,
"read the folder" means read everything, and you are back to the problem in the
last lesson.

If you use Obsidian, this is the same idea as a vault note that explains the
vault. Same job: orient before you dig.

## Tier 2 — Hot state

Read every run. Changes constantly. **Kept short on purpose.**

Your goals, your current numbers, and your inbox (`CHAIRMAN-NOTES.md`).
That is usually all.

The discipline here is unnatural: you will want to add context, history, and
caveats. Don't. Every line in this tier is paid for on every run forever. When a
hot file starts growing, that is the signal to move something out, not to accept
a longer file.

A good test: if your hot state is longer than about two pages, something in it
belongs in the record.

## Tier 3 — The record

Written often. Read almost never. Grows forever, and that is fine.

Your decisions and your meetings. The trick is **one dated file per meeting**,
not one growing meetings file:

```
BOARD-MEETINGS/
  2026-08-27.md
  2026-09-03.md
  2026-09-10.md
```

Now "what did we decide in September" is a small, cheap read, and no run ever
loads the whole history to write this week's report.

The decision log is the exception that stays as one file, because its value is
in being scannable top to bottom. So give it a rotation rule: when it passes
roughly 40KB, split off the completed year and leave a pointer.

## Tier 4 — Learned memory

This is the tier almost nobody builds, and it is the one that makes the system
get better instead of just longer.

Two files, and the split matters more than anything else in this lesson:

- **`CANDIDATES.md`** — lessons the board proposes. It writes here freely.
- **`LEARNINGS.md`** — lessons you have promoted. **Only you write here.**

Why split them? Because an agent that edits its own long-term memory without
review will, over time, come to believe things nobody checked. And afterwards
those beliefs look exactly like the ones that were verified. There is no way to
tell them apart later.

**Promotion needs the same lesson to show up in two independent runs.** One run
is an anecdote. The exception is a safety problem or a demonstrably false
instruction, which you fix immediately.

An empty `LEARNINGS.md` in month one is correct. Filling it early defeats the
rule it exists to enforce.

## Tier 5 — Procedure

Your playbooks. What the run actually does, step by step.

Read when running, not otherwise. The reason this is its own tier is that a
playbook is the thing you improve when a run goes wrong, and you want that to be
one obvious file rather than an instruction buried in a charter.

## The reading order

Tiers describe storage. This describes behaviour, and it is what you actually
put in your prompt:

1. **The inbox first** (`CHAIRMAN-NOTES.md`, which module 22 is about).
   Anything you left for it outranks everything else.
2. **Identity.** Who am I, what may I do.
3. **The playbook.** Run it.
4. **Write** to the record, propose into candidates.

That order is not arbitrary. Inbox first means the thing you cared about most
this week does not get buried under a routine report. Identity before action
means the guardrails are loaded before there is anything to guard.

## What this looks like assembled

```
ai-board/
  README.md                     <- tier 1, the index
  CHARTER.md                    <- tier 1, identity
  PROMOTION-LADDER.md           <- tier 1, what it must earn
  GOALS.md                      <- tier 2, hot
  METRICS.md                    <- tier 2, hot
  CHAIRMAN-NOTES.md             <- tier 2, hot. Your inbox to it
  DECISION-LOG.md               <- tier 3, record, rotates
  BOARD-MEETINGS/2026-08-27.md  <- tier 3, record, dated
  memory/CANDIDATES.md          <- tier 4, it proposes
  memory/LEARNINGS.md           <- tier 4, you promote
  PLAYBOOKS/WEEKLY.md           <- tier 5, procedure
```

Eleven files instead of four. Still all plain markdown, still all yours, and this
one is still working in month twelve.

<KeyPoint>Index, hot state, record, learned, procedure. Hot state is small because you pay for it every run; the record grows freely because it is dated and rarely read. The agent proposes into candidates and you promote into learnings, because memory an agent writes unsupervised becomes belief nobody checked.</KeyPoint>
