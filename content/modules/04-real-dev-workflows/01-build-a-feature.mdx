## The Full-Stack Feature Workflow

Building a feature with Claude Code follows a bottom-up pattern: schema → data layer → API → UI → tests. Each layer is reviewable before building the next.

## Example: Adding Notifications to a Web App

Let us walk through building a complete notifications feature from scratch.

<Callout type="tip">Break the feature into sub-tasks before you start prompting — write out the steps yourself (schema, types, server functions, API, hook, UI) and use each one as a separate prompt. This prevents Claude from jumping ahead and building on a shaky foundation.</Callout>

### Step 1: Database Schema

```
> I am adding user notifications to the app.
  Create SQL for a notifications table in Supabase:
  - id (uuid, primary key)
  - user_id (uuid, references auth.users)
  - message (text)
  - link (text, nullable)
  - is_read (boolean, default false)
  - created_at (timestamptz)
  
  Add RLS policy: users can only see their own notifications.
  Output as SQL ready to run in Supabase SQL editor.
```

Review the SQL. Run it in Supabase. Come back.

### Step 2: TypeScript Types

```
> Create @src/types/notification.ts with a Notification type 
  that matches the table we just created. Also create a 
  NotificationWithMeta type that includes a formatted 
  time_ago string.
```

### Step 3: Server Functions

```
> Create @src/lib/notifications.ts with these functions 
  using the service client from @/lib/supabase/server:
  - getNotifications(userId): returns Notification[]
  - markAsRead(notificationId, userId): returns { success }
  - markAllRead(userId): returns { count }
  - getUnreadCount(userId): returns number
```

### Step 4: API Routes

```
> Create @src/app/api/notifications/route.ts
  Following the same pattern as @src/app/api/progress/route.ts:
  - GET: returns notifications for the current user
  - PATCH: marks a notification as read (takes notificationId in body)
```

### Step 5: React Hook

```
> Create @src/hooks/useNotifications.ts
  - Fetches notifications from /api/notifications on mount
  - Provides markRead(id) and markAllRead() functions
  - Tracks unreadCount
  - Returns { notifications, unreadCount, markRead, markAllRead, loading }
```

### Step 6: UI Components

```
> Create @src/components/NotificationBell.tsx
  - Shows a bell icon with unreadCount badge
  - Clicking opens a dropdown list of notifications
  - Each item shows the message and a link if present
  - Uses the useNotifications hook
  - Follow the visual style of @src/components/ui/Button.tsx
```

### Step 7: Wire It Up

```
> Add NotificationBell to the header in @src/app/layout.tsx 
  next to the sign-out button. Import from @/components/NotificationBell
```

### Step 8: Manual Test

Now go to the browser and verify end-to-end:
1. Notifications endpoint returns data
2. Bell shows unread count
3. Clicking marks as read
4. Count updates

<Callout type="warning">Watch for scope drift during a feature build — if Claude starts suggesting "while we are here, we should also add X," that is a sign to redirect. Politely decline anything not in your sub-task list and add it to a follow-up prompt so it gets the focused attention it deserves.</Callout>

## The Vertical Slice Principle

Build one complete feature all the way through the stack before starting the next. A half-built feature in three layers is harder to debug than a complete feature in one.

## Summary

Schema → types → server functions → API routes → hooks → components → wire up → test. Each step is small, reviewable, and safe. This is how you ship reliable features fast.

<KeyPoint>Build features bottom-up, one layer at a time — schema first, then data functions, then API, then UI — and verify each layer works before building the next; this way mistakes are caught when they are cheap to fix, not after you have built six layers on top of them.</KeyPoint>
