## Start a Session

Open a terminal in a project directory — any project — and run:

```bash
cd /path/to/your/project
claude
```

You'll see the Claude Code prompt, with the version, current model, and working directory shown above it. Type `/help` for available commands, or `/resume` to pick up a previous conversation.

That's it. No project configuration, no indexing step, no setup wizard. Claude Code reads your project files as needed; you don't have to manually add context.

## Ask Before You Edit

Resist the urge to make it write code immediately. Spend your first few prompts reading.

```text
what does this project do?
```

```text
what technologies does this project use?
```

```text
where is the main entry point?
```

```text
explain the folder structure
```

This isn't ceremony. You are checking a hypothesis: **does this tool actually understand my codebase, or is it about to confidently pattern-match its way into a mess?** You already know what your project does. Ask anyway, and read the answer critically. If the summary is subtly wrong — wrong framework, wrong architecture, confidently describing a directory that does something else — you have learned something important before any file was touched.

You can also ask it about itself:

```text
what can Claude Code do?
```

```text
how do I create custom skills in Claude Code?
```

<Callout type="info">Claude Code doesn't load your whole repo into memory up front — it reads files as it needs them, using search and file reads like you would. That's why "what does this project do?" in a large monorepo takes a moment and produces a sketch rather than an exhaustive map. It's exploring, not indexing.</Callout>

## Pointing at Specific Files

Type `@` in the prompt to trigger file path autocomplete. This is how you aim.

```text
explain what @src/middleware.ts does
```

```text
compare @components/Button.tsx and @components/IconButton.tsx
```

Letting Claude find files itself works fine, and for exploratory questions it's often better. But when you already know where the relevant code lives, `@` skips the search and gets straight to the point — cheaper, faster, and less likely to drag in files you didn't want.

## Your First Code Change

Now ask for something small and real:

```text
add a hello world function to the main file
```

Claude Code will:

1. Find the appropriate file
2. Show you the proposed changes
3. Ask for your approval
4. Make the edit

That third step is the entire product. Claude Code always asks for permission before modifying files.

## The Approval Prompt

When Claude wants to edit a file, run a shell command, or make a network request, it pauses and asks you to approve. You'll get a choice: approve this action, decline it, or — for many actions — approve and stop being asked again.

The last option is the one to think about. "Yes, don't ask again" is a real time-saver once you know what you're doing and you've decided a particular action is safe in this repo. It is a bad idea on your first pass through unfamiliar work, because you're pre-approving a category of action based on a single example of it.

The honest framing: **each prompt is a place where you can still cheaply say no.** Once you start waving actions through, the cost of catching a bad change moves from "read three lines" to "read a diff and a git history." That's not an argument for maximum friction forever — it's an argument for spending the friction where it buys you something.

<Callout type="tip">If a proposed change looks off but you're not sure why, you don't have to decide immediately. Decline it and ask "why did you take that approach?" Claude will explain its reasoning, and you'll either learn something about the codebase or catch a bad assumption. Both are worth more than the thirty seconds.</Callout>

## Reviewing the Diff

Read the changed lines. Not the summary — the lines.

The failure mode with agentic coding tools is not that they write nonsense; it's that they write plausible code that's subtly wrong for your codebase. Uses a pattern you migrated away from. Duplicates a helper that already exists two directories over. Handles the happy path and quietly drops an error case. None of that reads as wrong in a prose summary. All of it is obvious in a diff.

<Callout type="warning">Slow down on any change touching authentication, payment logic, permissions, or database queries. These are the areas where a subtly wrong edit is both most likely and most expensive — and they're exactly the areas where a confident summary is least informative.</Callout>

## Ending a Session

- Type `/exit`, or press `Ctrl+D`
- `Ctrl+C` interrupts a running operation. If nothing is running, the first press clears your input and a second press exits
- `Esc` interrupts Claude mid-turn so you can redirect — the work done so far is kept

That last one is more useful than it sounds. When you see Claude heading somewhere wrong three tool calls in, you don't have to sit through it. Hit `Esc` and steer.

## Prompts That Work

Be specific. The docs' own example is a good one:

> Instead of: "fix the bug"
>
> Try: "fix the login bug where users see a blank screen after entering wrong credentials"

Break big work into steps rather than one enormous request:

```text
1. create a new database table for user profiles
2. create an API endpoint to get and update user profiles
3. build a webpage that allows users to see and edit their information
```

And let Claude explore before it changes anything — `analyze the database schema` before `add a migration` produces meaningfully better results than the reverse.

<KeyPoint>Read before you write: ask questions until you're satisfied Claude actually understands the project, then make one small change and read the diff line by line. The approval prompt is the cheapest place in the whole workflow to catch a bad idea — spend your attention there.</KeyPoint>
