## The Thing to Understand First

Before any of the modes, internalize this. From the official permissions documentation:

> Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what Claude Code allows.

Read that twice. It is the most important sentence in this module.

**CLAUDE.md is not a security boundary.** Writing "never touch the database" in your CLAUDE.md is a *request*. It influences what Claude attempts, the same way a good comment influences what a colleague attempts. It is not a wall. If Claude decides a database command serves your request, nothing in that file stops the call — only Claude Code's permission system does.

This matters because the intuition runs the other way. Writing a rule down *feels* like enforcing it. Developers absolutely do write safety rules into CLAUDE.md, feel protected, and act accordingly. The file is genuinely useful — just not for this.

To grant or revoke access, you have exactly four instruments: `/permissions`, permission rules in settings, permission modes, and `PreToolUse` hooks. Prose is not on the list.

<Callout type="warning">The dangerous version of this mistake is prompt injection. If Claude reads a file, a web page, or an issue comment containing hostile instructions, your CLAUDE.md is not what decides whether those instructions get acted on. Your permission configuration is. Content Claude reads is data, and data can lie.</Callout>

## The Six Modes

Each mode is a different tradeoff between how often you're interrupted and how much you're watching.

| Mode | What runs without asking | Best for |
|---|---|---|
| `default` | Reads only | Getting started, sensitive work |
| `acceptEdits` | Reads, file edits, and common filesystem commands (`mkdir`, `touch`, `mv`, `cp`) | Iterating on code you're reviewing |
| `plan` | Reads, plus classifier-approved commands when auto mode is available | Exploring a codebase before changing it |
| `auto` | Everything, with background safety checks | Long tasks, reducing prompt fatigue |
| `dontAsk` | Only pre-approved tools | Locked-down CI and scripts |
| `bypassPermissions` | Everything | Isolated containers and VMs only |

One naming quirk to get straight: **the mode that reviews every action is labeled Manual** in the CLI, in `claude --help`, in the VS Code and JetBrains extensions, and in the desktop app. Its config value is `default`, which is what hooks and SDK integrations use. `manual` is accepted as an alias wherever you type the value. So `default` and Manual are the same mode — you'll see both.

### Which mode you start in

This one is worth checking rather than assuming, because it changed. On Pro, Max, and Team
plans, recent versions of Claude Code start a new terminal session in **auto mode** — not
Manual. On older versions, and where auto mode isn't available to your account, sessions
start in Manual.

So the first thing to do on launch is read the status bar. `⏸ manual mode on` means every
action comes to you. `⏵⏵ auto mode on` means the classifier is reviewing actions instead of
you. Those are very different sessions, and which one you get depends on your plan and your
installed version.

If you want Manual, press `Shift+Tab` once, or start with `claude --permission-mode default`.
A session you resume keeps the mode it was in.

<Callout type="note">Startup precedence, highest first: the `--permission-mode` flag (or `--dangerously-skip-permissions`), then `permissions.defaultMode` in settings, then the built-in default. One exception worth knowing: an `"auto"` value in `.claude/settings.json` or `.claude/settings.local.json` is ignored, so a repository you clone cannot grant itself auto mode.</Callout>

## What Each Is Actually For

**`default` / Manual.** Every action, your call. This is where you return for anything you'd be unhappy to explain later — and, on plans and versions that don't start you in auto mode, where you begin.

**`acceptEdits`.** Claude creates and edits files in your working directory without prompting, plus common filesystem Bash commands. The scope matters: auto-approval applies only to paths inside your working directory or `additionalDirectories`. Anything outside that scope, and other Bash commands, still prompt. Use it when you intend to review the result in your editor or `git diff` rather than approving each edit inline. That's the trade — you're not skipping review, you're batching it. If you're not actually going to read the diff, you've just turned review off.

**`plan`.** Claude reads files, runs shell commands to explore, and writes a plan — but does not edit your source. When the plan is ready, it presents it and asks how to proceed. Edits stay blocked until you approve.

**`auto`.** Auto-approves tool calls, with a separate classifier model reviewing actions before they run and blocking anything that escalates beyond your request or looks driven by hostile content Claude read. It is genuinely more thoughtful than "yes to everything." It is also, per the docs' own warning, not a safety guarantee — use it where you trust the direction, not as a substitute for review on sensitive operations. Availability depends on your plan, provider, and model.

**`dontAsk`.** The inverse of bypass. Every tool call that would prompt is *auto-denied* instead. Claude runs only what matches your `permissions.allow` rules and the built-in read-only commands. Made for CI and restricted environments where the session can never wait for input. The failure mode is a refusal, not a disaster — which is the right failure mode for automation.

**`bypassPermissions`.** Covered below, honestly.

<Callout type="info">In every mode except `bypassPermissions`, writes to protected paths are never auto-approved — that's `.git`, `.config/git`, `.claude`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn` and a set of protected files. This guards repository state and Claude's own configuration from accidental corruption. Note the exception in that sentence, because it's the whole point of the next section.</Callout>

## bypassPermissions, Honestly

`bypassPermissions` disables permission prompts and safety checks so tool calls execute immediately. The docs are unambiguous about where it belongs:

> Only use this mode in isolated environments like containers, VMs, or dev containers without internet access, where Claude Code cannot damage your host system.

And:

> `bypassPermissions` offers no protection against prompt injection or unintended actions.

Three specifics people get wrong:

**It does not protect your protected paths.** This is the one mode where protected-path writes are *allowed*. `.git`, `.claude`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn` — all writable, no prompt. The safety net you assumed was structural is mode-dependent.

**A few things still prompt.** Explicit `ask` rules, connector tools your organization set to `ask`, and MCP tools marked `requiresUserInteraction` still force a prompt. Removals targeting the filesystem root or home directory — `rm -rf /`, `rm -rf ~` — still prompt as a circuit breaker against model error. That circuit breaker is not a safety feature you should feel good about. It is the floor, not the floor plan.

**You can't drift into it.** You cannot enter `bypassPermissions` from a session started without an enabling flag; you have to restart with `--permission-mode bypassPermissions` (or the equivalent `--dangerously-skip-permissions`). On Linux and macOS, Claude Code refuses to start in this mode as root or under `sudo`. Administrators can block it entirely with `permissions.disableBypassPermissionsMode: "disable"` in managed settings, and can disable auto mode with `permissions.disableAutoMode`.

If what you want is "far fewer prompts," `auto` is the mode you actually want. `bypassPermissions` is for throwaway environments where the blast radius is the container.

## Switching Modes

Press **`Shift+Tab`** during a session to cycle. If you're starting in auto mode, the first press drops you to `default`; from there the cycle runs `default` → `acceptEdits` → `plan` → back to `default`. The current mode appears in the status bar as `⏸ manual mode on`, `⏵⏵ accept edits on`, `⏸ plan mode on`, or `⏵⏵ auto mode on`.

Not every mode is in that cycle by default. `dontAsk` never appears — set it with `--permission-mode dontAsk`. `bypassPermissions` only appears after you start with an enabling flag. `auto` appears when your account meets its requirements.

At startup:

```bash
claude --permission-mode plan
```

As a persistent default, set `defaultMode` in settings:

```json
{
  "permissions": {
    "defaultMode": "plan"
  }
}
```

<Callout type="tip">The mode is set through these controls — not by asking Claude in chat. "Please be careful and ask me before editing anything" is a request to the model, not a change to the permission system. `Shift+Tab` is.</Callout>

## Permission Rules

Modes set the baseline. Rules layer on top, in `allow`, `ask`, and `deny` lists. Manage them interactively with `/permissions`, or write them in settings.

The syntax is `Tool` or `Tool(specifier)`:

| Rule | Effect |
|---|---|
| `Bash` | Matches all Bash commands |
| `Bash(npm run build)` | Matches the exact command `npm run build` |
| `Bash(git push *)` | Matches git push commands |
| `Read(./.env)` | Matches reading `.env` in the current directory |
| `WebFetch(domain:example.com)` | Matches fetch requests to example.com |

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Bash(git commit *)"],
    "deny": ["Bash(git push *)"]
  }
}
```

Two details that will bite you:

- **The space before `*` matters.** `Bash(ls *)` matches `ls -la` but not `lsof`. `Bash(ls*)` matches both.
- **Deny rules and explicit `ask` rules apply in every mode**, including `bypassPermissions`. Allow rules have no effect in that mode, because everything is already approved. If you want a hard guarantee about one specific thing, a deny rule is the instrument — not a sentence in CLAUDE.md.

## The Habit Worth Building

**Default to `plan` mode in code you don't know.**

The reasoning is economic. In plan mode, a wrong idea costs you a read. In `acceptEdits`, a wrong idea costs you a diff review and a revert. The gap widens the less you know about the codebase — which is exactly when your judgment about whether Claude's approach is right is weakest. Plan mode front-loads the cheap check.

There's a second effect that's harder to quantify and matters more: a written plan is reviewable in a way that a stream of edits isn't. You can read a plan and notice "it's going to touch the auth middleware, why?" before a single line changes. You can't easily notice that in real time while approving your ninth edit prompt.

Set it as your project default and opt *out* deliberately:

```json
{
  "permissions": {
    "defaultMode": "plan"
  }
}
```

## Before You Point an Agent at a Repo

We put together a [preflight checklist](/downloads/preflight-checklist.md) — our own, not an Anthropic document — covering what to verify before letting an agent touch a repository. Clean working tree, permission configuration reviewed, deny rules in place for anything genuinely irreversible, and a clear answer to "what's the worst thing that happens here."

It takes two minutes and it is mostly the questions you'd ask anyway, in an order that means you don't skip the third one.

<KeyPoint>Permission rules are enforced by Claude Code, not the model — CLAUDE.md shapes intent, not access.
